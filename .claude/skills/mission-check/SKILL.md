---
name: mission-check
description: Lint a sw.models unit mission, frag order, task or skill in the working tree (mission_check + checkpoint_lint) and explain each finding with the forge kit rules (MISSIONS.md, FRAGORDERS.md, CHECKPOINTS.md). Use when the user asks whether a mission or frag order is well formed, why a parameter is not passed, whether a mission ends, what a frag order's kind is or why nothing handles it, or whether a skill / task / frag order survives a checkpoint save + resume. Usage /mission-check <mission name | frag-order name or dia-type | task | skill> [--root <sw.models copy>]
argument-hint: <"mission name" | "frag order" | dia-type | task a.b.C | skill a.b.C> [--root <path>]
---

Lint and explain, inline (no subagent). Target: $ARGUMENTS

1. **Context** (one Bash call): `git -C C:/MASARepo/sw.models branch --show-current && git -C C:/MASARepo/sw.models rev-parse --short=10 HEAD && git -C C:/MASARepo/sw.models status --short -- data/data/models | head -5`. The tools read the working tree, so uncommitted edits count. With `--root`, lint that copy instead.
2. **Kind of target**: a name with spaces or a `PREFIX - ` form is a mission or a frag-order name: grep `C:/MASARepo/forge/docs/sw.models/mission_index.md` (§2 missions and §6 frag orders both have `^| mildb | "<name>" |` rows; the section tells them apart) or `name="<name>"` in the DB's Missions.xml (`<mission` vs `<fragorder`). A CamelCase or `Rep_OrderConduite_*` name is a frag-order dia-type. A dotted name is a task if `<task` is the root of its XML (a/b/C.xml under dia5), else a skill; a dotted frag-order dia-type (kind (c), the task name) can be linted both ways. If unsure, grep §3 `^| .<skill>. ` too.
3. **Run** from `C:/MASARepo/forge`:
   - mission: `python -I tools/mission_check.py --mission "<name>" -v [--root R]`, then `python -I tools/checkpoint_lint.py --task <its dia-behavior> [--root R]`;
   - frag order (name or dia-type): `python -I tools/mission_check.py --fragorder "<name>" -v [--root R]`, then `python -I tools/checkpoint_lint.py --fragorder "<name>" [--root R]` (the started task's closure and the kind-(b) readers);
   - task: `python -I tools/mission_check.py --task <task> -v [--root R]` and `python -I tools/checkpoint_lint.py --task <task> [--root R]`;
   - skill: `python -I tools/checkpoint_lint.py --skill <skill> [--root R]`.
4. **Explain** each ERROR / WARN in one or two lines: the rule and its anchor from `C:/MASARepo/forge/docs/sw.models/MISSIONS.md` (§1 files, §2 parameters and `NIL`, §3 task rules, §5 checks), `C:/MASARepo/forge/docs/sw.models/FRAGORDERS.md` (§2 kinds — the tool's kind codes are listed in §8 —, §3 availability, §5 frago tasks, §6 automats and crowds, §7 readers, §8 checks) or `C:/MASARepo/forge/docs/sw.models/CHECKPOINTS.md` (§3 hazard row: effect, model-side fix; §6 when it is a sim-side gap; §7 for a frag order: the fix pair and the per-kind recommendation in §7.4). Checkpoint findings are **upper bounds**: open the Lua at the reported line and say whether the hazard is real. Notes (`-v`) only when relevant (continuous missions, cross-DB id differences, a task named by the dia-type reachable on a commander).
5. **Answer**: first line `sw.models <branch> @ <commit>` (or the root); for a frag order, its kind, what it starts or who reads it, and its checkpoint class; then a table finding → real? → fix (model-side, or sim-side gap); then the ant targets that would or would not catch the rest (`MISSIONS.md` §5, `FRAGORDERS.md` §8). Do not edit files; for a fix, show the diff. Deeper work (a rewrite, a new mission or frag order) → suggest `/mission` or `/fragorder` (writes) or `/models` (read-only proposal).
