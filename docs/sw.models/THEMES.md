# sw.models theme map

Purpose: save the navigator its first few searches. Theme → search words → where to start in the files.
**No behavior is described here**: read the files. Paths and anchors are checked by `tools/check_themes.py`; no line numbers.

Path aliases (the checker expands them): `dia5/` = `data/data/models/ada/decisional/dia5/` · `dec/` = `data/data/models/ada/decisional/` ·
`phy/` = `data/data/models/ada/physical/mildb/` · `wwt/` = `data/data/models/ada/physical/worldwide-tests/` ·
other paths are relative to the sw.models root unless prefixed `sw.sword/`, `directai/`.
`file::text` = an anchor: that text occurs in that file (or anywhere under that dir).
Paths are for the standing model `ada` on the branch the index was built from; client branches add other model dirs
(see gotchas). Entity names map to files: name a.b.C = file dia5/a/b/C.xml (+ C.lua).
[branch-specific] on a line = some of its paths are absent on older client branches (checked with
`python -I tools/check_themes.py --ref <branch> sw.models`); verify with `git ls-tree` on the user's branch.
Orientation docs in the repo: `README.md`, `ARCHITECTURE.md` (layout, build, checks; accurate except "entities are paired .lua + .xml", false for tasks). [branch-specific]

## Vocabulary

French (physical DB, legacy dia-types, sw.soult): Pion = unit (agent) · Automate = automat (unit group with a CP; "commander" in dia5) ·
Composante = equipment · Dotation = resource/supply item · Capteur = sensor · Armement = weapon system · Lanceur = launcher ·
Modèle (décisionnel) = decisional model (`Models.xml`) · Ordre de conduite (`Rep_OrderConduite_*`) = frag order · Embarquer / Débarquer = mount / dismount ·
Fuseau = AOR · Lima = phase line · Conduite = conduct (automat CDT phase) · MRT = automat phase that creates subordinate missions.

Model terms: **entity** = one Spark XML (+ Lua) file, kind given by its root element: `skill`, `task`, `query`, `role`, `resource`, `class`, `interface` ·
**family** = top dir of `dia5/` (`common`, `military`, `mildb`, `security`, `navy`, `crowd`, `test`) · **agent** vs **commander** = unit vs automat side ·
**primitive** / **action** skill = skills under `skills/primitives/` and `skills/actions/` (actions acquire resources) ·
**link** = a skill's sub-skill (`<link name target>`, `skill.links.<name>` in Lua) · **feedback** = signal a skill sends up (`Feedback( self.feedbacks.x )`) ·
**stage** = sequential step of a task (`<stage label>`), its behaviors run in parallel · **metadata class** = a task's Lua-side companion class (`tasks/knowledge/`) ·
**body type** = the world class a skill/role runs on (usually `common.agent.world.MeKnowledge`; `meKnowledge` in Lua) ·
**decisional model** = `Models.xml` entry binding a role (`dia-type`) to a mission list; units pick one with `decisional-model`.

## Gotchas you would not think to grep for

Each line: the trap, then an anchor to start reading. Re-verify before quoting.

- **An entity's `name` must equal its path under `dia5/`** (dots for slashes); the index relies on it. → `dia5/common/agent/behaviors/skills/actions/Activate.xml::name="common.agent.behaviors.skills.actions.Activate"`
- **Tasks have no Lua.** Task logic is in its skills and in its metadata class (`spark.metadata-class` → `tasks/knowledge/<X>.lua`). → `dia5/military/agent/tasks/AttackObjective.xml::spark.metadata-class`
- **The mission → task link is `dia-behavior`, not `dia-type`** (they can differ); automat missions use `mrt-dia-behavior` and `cdt-dia-behavior`. → `phy/Missions.xml::dia-type="agent.behaviors.tasks.PerformAWork_dike"`, `sw.sword/src/libraries/simulation/Entities/Automates/DEC_AutomateDecision.cpp::ePhaseCDT`
- **A mission is only available to a unit if its decisional model lists it by name** in `Models.xml`, whose `dia-type` is a **role** (not a task). A mission name appears in `Missions.xml`, `Models.xml` (once per model), `Locales/fr/Missions_fr.ts` and `Mission sheets/`. → `phy/Models.xml::<mission name="COMBAT - Attack objective">`
- **Sensors, weapons and resources live on the equipment, not the unit**: a unit lists only equipment types and counts; grep each `type=` in `Equipments.xml`. → `phy/Equipments.xml::<weapon-system launcher="12.7-mm Cupola Machine Gun"`
- **Find a unit kind by `nature-app6`, not by name**: spellings vary between DBs ("Mechanised" in mildb, "Mechanized" in wwt) and several types share a nature. One model name can serve 2 units in one DB and 125 in another. → `phy/Units.xml::infantry/mechanized`, `phy/Models.xml::name="Infantry platoon"`
- **ada has two physical DBs** that differ (missions, models, frag orders): `mildb` and `worldwide-tests`. Check both. → `wwt/physical.xml`, `build/build.xml::checkstage base="worldwide-tests"` [branch-specific]
- **Client models are whole model dirs on their branch** (`DB-6.26.2`, `mcast_v3`, `USMC`, …), with their own decisional and physical DBs; `ada/decisional/extensions/` holds only a readme. → `dec/extensions/readme.txt::client decisional models`
- **`taskgroup.*` tasks and roles live in a git submodule**, empty unless initialised: unresolved in grep, not an error. → `.gitmodules::sw.taskgroup-decisional`
- **Frag orders start tasks through `FragOrder.lua`**: `dia-type` → `fragOrderTaskInitializers` entry → task; no entry → `integration.startFragOrder`. Client extensions add entries through `extensionsFragosInit`. → `dia5/FragOrder.lua::fragOrderTaskInitializers`, `dia5/FragOrder.lua::extensionsFragosInit`
- **Frag orders allowed during a mission are listed per model**, as `<fragorder name>` children of that model's `<mission>` in `Models.xml`; the same mission can allow different ones per model and DB (index §7 "Frag orders" column). Model-level `<fragorders>` are available without a mission. → `phy/Models.xml::<fragorder name="Use infiltration path"/>`
- **Many frag orders start no task: skills poll them.** Their initializer is empty or only cleans the order, so an empty index "Frago"/"Starts" cell does not mean "not reactive" (e.g. `Infiltrate` read in `MoveAndTakePosition`, `ResumeMovement`/`CrossDepartureLine` in `PhaseLine:needToWaitForCoordination`). → `dia5/common/agent/behaviors/skills/actions/MoveAndTakePosition.lua::getInfiltrateFragOrder`, `dia5/common/agent/world/PhaseLine.lua::needToWaitForCoordination`
- **Commander skills name unit missions by `dia-type` in `<string>` values** (`;`-separated, params like `mainTasks`), resolved at runtime to the task through `Missions.xml`. The dia-type usually equals the task name but not always, so a task rename that keeps the dia-type leaves them valid, and a dia-type rename breaks them silently. → `src/checkdec/tasks.go::mainTasks`, `sw.sword/data/app-data/resources/integration/CommunicationIntegration.lua::integration.getAgentTaskKnowledge = function( entity, diaType )`, `phy/Missions.xml::dia-type="agent.tasks.Reconnoitre_trafic"`
- **Translations, mission sheets and decisional models are keyed by mission name**, not by task or dia-type: a task rename touches only `dia-behavior` (both DBs); a mission rename touches `Missions.xml`, `Models.xml`, `Locales/fr/Missions_fr.ts`, `Mission sheets/`. `wwt/` has no `Locales/`. → `phy/Locales/fr/Missions_fr.ts::<source>ENGINEER - Reconnoiter</source>`, `phy/Missions.xml::name="ENGINEER - Reconnoiter"`
- **Lua refers to tasks by string and to queries by bare dotted name** (`common.agent.queries.getX( {…} )`): grep the full dotted name, not the file name. → `dia5/common/agent/behaviors/skills/BreachObjectAlongRoads.lua::common.agent.queries.getAreasToBreachObjectAlongRoads(`
- **Models never call `DEC_*` directly**; only `integration.*` (enforced by `checkdec.py` against `decfunctions.txt`). → `build/checkdec.py::don't directly call DEC functions`
- **`FragOrder.lua` overrides `integration.*` functions** at load time (model-side override of the layer). → `dia5/FragOrder.lua::integration.startFragOrderTask = fragOrder.startFragOrderTask`
- **Families may only depend on allowed families** (common → none; military, security, crowd → common; mildb, navy → common + military). → `build/checkPackages.py::authorisedPackages[ "navy" ]`
- **Every `<stage label>` must exist in each DB's `Stages.xml`** (`ant generate-stages` fixes it); `dia5/test/` is ignored. → `src/checkstage/stage.go::stage label=`, `build/build.xml::generate-stages` [branch-specific]
- **`checkdec tasks` only warns** (`failonerror="false"`): a stale `dia-behavior` gives a warning, and its `mainTasks` cross-check reads an old task shape (`stages>skills>skill`), so it sees nothing in current tasks. Nothing in `ant check` fails on a broken rename; run the mission. → `build/build.xml::failonerror="false"`, `src/checkdec/tasks.go::does not exist but is`, `src/models/decdb.go::skills>skill`
- **Name case: the sim resolves entity names case-insensitively, the validator compares type names exactly**, and sparkcheck resolves by file existence (passes on Windows). So the two tasks citing their metadata class with the wrong case (`BypassObjects` vs `ByPassObjects`) load fine, but a mis-cased type can give a spurious type mismatch where names are compared. Index §10 lists such mismatches. → `dia5/mildb/agent/tasks/ByPassObjects.xml::mildb.agent.tasks.knowledge.BypassObjects`, `directai/src/libraries/plugins/spark/library.lua::string.lower( name )`, `directai/src/libraries/spark/validation/utilities.lua::ot1 == ot2`
- **`decisional.xml` is generated and gitignored** (`gendec`, `ant configure`); its `model-version` gates sim startup. → `.gitignore::decisional.xml`, `sw.sword/src/libraries/simulation/Decision/DEC_Workspace.cpp::model-version`
- **"Mount/Dismount" = the unit's own vehicles; "Embark/Disembark/Load/GetTransported" = carried by another unit** (French "embarquer" covers both). → `dia5/common/agent/behaviors/skills/actions/Mount.xml::dismounted state into mounted state`, `dia5/common/agent/behaviors/skills/actions/GetTransported.xml::ready to be transported`
- **Bug: frag order `SafetyDismount` mounts the unit**: its task runs `actions.Mount` (and `frago.Mount`'s description says "dismount"). → `dia5/security/agent/behaviors/frago/Dismount.xml::common.agent.behaviors.skills.actions.Mount`
- **Role Lua maps ontology types** for the integration layer (`sw.ai.setRoleProperties`, opaque to directai). Only 14 of 32 roles have Lua; the others inherit the nearest parent's map (and `<body-type>`). `integration.ontology.types.<key>` is read live from the current brain's role; a key missing from the map falls back to `sparkle.Object` (no model methods): e.g. `liaisonInstance`, `transmitterType` in ada. → `dia5/military/agent/roles/Agent.lua::sw.ai.setRoleProperties`, `sw.sword/data/app-data/resources/Integration.lua::local ontologyKeys = {`, `dia5/common/agent/world/FragOrder.lua::integration.ontology.types.transmitterType`
- **173 "classes" = 41 world classes + 132 task-metadata classes** (chain to `sparkle.TaskMetadata` through `PlatoonTask` / `CompanyTask`, in `tasks/knowledge(s)/`). Count and refactor them separately. → `dia5/common/agent/world/PlatoonTask.xml::<extends>sparkle.TaskMetadata</extends>`
- **A class `.lua` may only define methods declared in its own XML** (`class.lua.method.missing-declaration`, even when an interface or the parent declares it), must define every own non-abstract one, and a concrete class must re-declare (non-abstract, in its own or an ancestor's XML) each method of its interfaces (`class.method.unimplemented`). `<constructor>` ⇔ `__init`. Moving a method = edit both XML and Lua of both classes. → `directai/src/libraries/spark/validation/messages.lua::class.lua.method.missing-declaration`, `directai/src/libraries/spark/validation/validators/object.lua::local uncheckedMethodNames`
- **`super` must be captured at file top** (`local super = __super`; `__super` exists only while the file loads and is nil in sparkcheck); `super( self ):m()` calls the parent's `m`. → `dia5/common/agent/world/AircraftTransporterMeKnowledge.lua::local super = __super`, `directai/src/libraries/spark/validation/validators/object.lua::definer( "__super"`
- **Abstract base classes leave interface methods to subclasses** (`Element`, `LocalizedElement`: `getPosition` is abstract), so "who implements X" means the concrete subclasses. → `dia5/common/agent/world/LocalizedElement.xml::name="getPosition" abstract="true"`
- **`interfaces.Agent` has no direct implementer**: `Agent` / `AgentKnowledge` get it only through `Teammate` / `NonTeammate` (both 0-method markers extending it), so merging or dropping either loses `interfaces.Agent` for that class. Interface "facets" of the universal `Object` class (`Fire`, `CheckPoint`, `DecontaminationPlot`, `UndergroundNetwork`) filter nothing at run time: the `object` key wraps every object knowledge as `Object`. → `dia5/common/agent/world/interfaces/NonTeammate.xml::<extends>common.agent.world.interfaces.Agent</extends>`, `dia5/military/agent/roles/Agent.lua::common.agent.world.Object,`
- **World objects are cached per brain by sim entity, not by type**: `CreateKnowledge( typeB, src )` after `typeA` returns the typeA object; mission parameters are wrapped by Missions.xml type (`Path`/`Line`/`Itinerary` → a list of `point`, not `itinerary`). → `sw.sword/data/app-data/resources/integration/SimulationIntegration.lua::localStorageVar.knowledgeCache[ knowledgeSource ]`, `sw.sword/src/libraries/simulation/Decision/DEC_Decision.cpp::functorsBM[ "Path" ] = PathFunctionBM`
- **Role body type is checked statically only against the role's own `<skills>`**; skills reached through tasks or links are checked only at runtime with type checking on. → `directai/src/libraries/spark/validation/validators/role.lua::checkSkillBodyTypeConstraints`
- **`sparkcheck` runs with a mock environment**: a load-time global missing from it fails the check. → `dia5/.validation.lua::Validation environment`
- **Translations are fixed by loading and saving the DB in SWORD Adaptation**, not by hand. → `build/build.xml::Fix translations` [branch-specific]
